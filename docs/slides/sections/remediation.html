Remediation Pipeline

From CVE to Pull Request

The remediation agent is a SequentialAgent that orchestrates three phases: initial planning, iterative build verification, and PR creation. Each phase is a distinct sub-agent wired together by ADK’s sequential execution model.

Phase 1: Initial Planning

🛠 initial_remediation_planner

The planner loads the maven-remediation and scm-conventions skills via SkillToolset, clones the repository, analyzes the CVE, edits pom.xml using OpenCode (via execute_bash), and runs mvn verify to check the build.

Tools:

SkillToolset execute_bash (build_bash_tool) clone_repository

Gates:

before_agent_callback → pre_gate_callback after_agent_callback → post_gate_callback

The pre-gate validates the CVE ID, Maven coordinates, and versions before the LLM spends any tokens. Invalid requests get a guidance-only response at zero model cost.

Phase 2: Build Retry Loop

🔄 remediation_retry_loop · LoopAgent (max_iterations=3)

If the initial build fails, the LoopAgent retries up to 3 times. Inside the loop, BuildResultChecker (a BaseAgent) inspects the build output. On success it escalates to exit the loop. On failure, the remediation_retry_planner gets another attempt with the error context from the previous run.

Phase 3: PR Creation

📦 remediation_pr_opener

Stages changed files (pom.xml, REMEDIATION.md), commits, pushes to a branch named rhtpa/remediate-<cve_id>-<timestamp>, and opens a pull request via create_pull_request tool (uses glab/gh CLI). The base branch is configurable via SCM_BASE_BRANCH env var.

What execute_bash Actually Does

⚠ NOT ADK’s built-in ExecuteBashTool

This is a custom FunctionTool built by build_bash_tool() in app/config.py. ADK’s ExecuteBashTool requires user confirmation for every command — unusable in CI/CD. The custom tool uses policy-based safety instead:

Allowed command prefixes:

opencode mvn git cd sed cat ls head grep find

Timeout: 300 seconds. Memory limit: 1 GB. This is how the agent runs OpenCode for code edits and Maven for build verification.

Why the retry loop matters: First-attempt build success rate for Maven dependency changes is not 100%. Transitive dependency conflicts, BOM-managed version overrides, and module compatibility issues all cause initial build failures. The LoopAgent gives the agent 3 chances to get it right, with full error context from each failed attempt.
